Virtualisation

BTS SIO - Révision Complète

1. Concepts Virtualisation

Virtualisation : Créer une représentation logicielle (virtuelle) d'une ressource physique. VM = machine virtuelle. Separates logique du matériel.
Avantages : Consolidation (plusieurs VMs sur une machine physique), flexibilité (créer/supprimer VMs rapidement), isolation (VMs indépendantes), économies (moins de matériel), migration facile, snapshots (sauvegardes rapides).
Exemple virtualisation : Avant : 5 serveurs physiques → 5 machines, 5 X électricité, refroidissement, espace Après : 5 VMs sur 1 serveur physique puissant → 1 machine, 1 X électricité, 1 OS Hyperviseur orchestre les ressources : - Processeur : divise CPU physique en vCPUs (virtual CPUs) - Mémoire : alloue vRAM à chaque VM - Stockage : partage disque physique

2. Hyperviseurs Type 1 vs Type 2

Type 1 (Bare Metal) : S'exécute directement sur matériel (pas d'OS). Exemples : vSphere (VMware), Hyper-V (Microsoft), XEN. Serveurs/data centers.
Type 2 (Hosted) : S'exécute dans un OS (Windows, Linux). Exemples : VirtualBox, VMware Workstation, Parallels. Postes de travail, développement.
Type 1 (Hyperviseur bare metal) : Hardware → Hyperviseur (vSphere) → VMs - Directement sur matériel = accès direct ressources - Meilleure performance (pas d'OS overhead) - Utilisé en production Type 2 (Hyperviseur hébergé) : Hardware → Windows/Linux (OS hôte) → VirtualBox → VMs - Via un OS = plus de latence - Performance inférieure (couche OS supplémentaire) - Utilisé en développement/test

3. Ressources Virtuelles : vCPU, vRAM, Storage

vCPU (Virtual CPU) : Part du processeur physique allouée à une VM. 1 vCPU = 1 cœur logique. VM peut avoir 1-8 vCPUs selon besoin. Oversubscription possible (total vCPUs > CPU physique) si pas utilisation 100% simultanée.
vRAM (Virtual RAM) : Mémoire allouée à VM. Ex: VM Win Server = 4 GB vRAM. Total vRAM sur serveur ≤ RAM physique. Allocation statique ou dynamique.
vStorage : Disque virtuel (fichier .vmdk ou .vdi). Thin provisioning = alloue espace seulement si utilisé. Thick = alloue tout l'espace d'avance.
Configuration exemple VM Web Server : vCPU : 2 (processeur dual-core virtuel) vRAM : 2 GB (2048 MB) vStorage : 40 GB thin provisioning → Fichier vmdk de ~5 GB initial → Grandit au fur à mesure (jusqu'à 40 GB max) → Économise espace disque host Configuration exemple VM Base données : vCPU : 4 vRAM : 8 GB vStorage : 200 GB thick (allocé entièrement)

4. Modes Réseau : Bridge, NAT, Host-Only

Bridge : VM connectée comme un périphérique physique sur le réseau réel. Obtient IP du réseau (DHCP ou static). Visible par autres machines (ex: 192.168.1.100).
NAT (Network Address Translation) : VM accède au réseau via l'hôte (adresse traduite). VM a IP virtuelle privée (ex: 192.168.122.10). Hôte = passerelle. Machines externes ne voient pas la VM.
Host-Only : VM ne communique qu'avec l'hôte et d'autres VMs host-only. Aucune connexion réseau externe. Utilisé pour isolation total (lab de sécurité).
Bridge : VM (192.168.1.100) ← → Switch réel ← → Réseau (192.168.1.0/24) Autre PC sur réseau peut pinguer la VM directement NAT : VM (192.168.122.10) ← → Hôte (192.168.1.50) ← → Réseau Requête VM → Hôte traduit source → Envoie réseau Réponse réseau → Hôte traduit destination → Retour à VM Réseau ne voit que l'hôte, pas la VM Host-Only : VM ← → Hôte (réseau virtuel interne) Pas d'accès réseau externe Idéal pour test en isolation

Exercice 1 : Dimensionnement VM
Serveur physique : 16 cores CPU, 64 GB RAM. Créer 3 VMs : Web server, Database, Active Directory. Allouer ressources optimales.
Correction :

Répartition ressources :

VM Web Server (charge modérée) :
vCPU : 2 cores
vRAM : 4 GB
vStorage : 50 GB

VM Database (critique, charge élevée) :
vCPU : 8 cores (half du serveur)
vRAM : 32 GB (half RAM)
vStorage : 200 GB

VM Active Directory (léger) :
vCPU : 2 cores
vRAM : 4 GB
vStorage : 30 GB

Total utilisé : 12 vCPU (75% serveur), 40 GB RAM (62.5%), 280 GB storage

Avantage : Réserve 4 cores et 24 GB pour pics d'utilisation, équilibrage charge
Exercice 2 : Choix Mode Réseau
Vous configurez une VM Linux test. Vous besoin : accéder à VM depuis PC physique ET depuis autres VMs. Quel mode réseau choisir et pourquoi ?
Correction :

Besoin : VM accessible depuis hôte ET d'autres VMs

Analyse modes :

Bridge ✓✓
- VM obtient IP réseau réel (ex: 192.168.1.100)
- Hôte peut pinguer VM (sur même réseau)
- D'autres VMs bridgées peuvent communi quer avec elle
- Visible sur réseau physique

NAT ✗
- VM isolée (IP virtuelle 192.168.122.10)
- Hôte peut accéder NAT forward ports
- Mais autres VMs ne voient pas cette VM en NAT

Host-Only ✓ (partiellement)
- VM et hôte communiquent
- Autres VMs host-only peuvent communi quer\n - Mais si autre VM est en Bridge = pas de communication

MEILLEUR CHOIX : Bridge
Raison : Simule machine physique complète, accessible par tous
Exercice 3 : Thin vs Thick Provisioning
Vous avez 500 GB de stockage pour créer 5 VMs de 100 GB chacune. Comparez thin et thick provisioning en termes d'espace et performance.
Correction :

Thin Provisioning :\n - Allocate logiquement 100 GB à chaque VM
- Physiquement : seulement espace utilisé est écrit
- Exemple après création (disques vierges) : ~50 GB utilisés\n - Total 5 VMs thin : 250 GB physique disponible\n - Avantage : économie massif espace (250 vs 500 GB)\n - Risque : si VMs grandissent simultanément → saturation disque\n - Performance : Très bonnes (allocation à demande)\n

Thick Provisioning :\n - Allocate immédiatement 100 GB physique par VM
- Total 5 VMs : 500 GB disque utilisés
- Tous VMs fullSpeed dès création
- Avantage : Pas de risque saturation, performance garantie\n - Inconvénient : gaspille espace si VMs < 100 GB

RECOMMANDATION : Thin pour la plupart, Thick pour VMs critiques (database)
Exercice 4 : Snapshot et Snapshot Management
VM en production avant update système. Créez snapshot, effectuez update, si problème rollback. Décrivez processus et limitations.
Correction :

Processus Snapshot :

1. Avant update :
Hyperviseur → "Créer snapshot "Avant-Update"
Capture état exact VM : disque + mémoire (état CPU) + configs
Fichier delta créé (~10 GB pour 50 GB disque)

2. Update système :
VM s'exécute normalement
Les changements écrits à un nouveau fichier delta
Snapshot ancien reste intouché

3. Problème détecté :
"Rollback" au snapshot "Avant-Update"
Hyperviseur désactive delta update, réapplique ancien snapshot
VM revient exactement état d'avant (< 1 minute)

4. Succès :
"Consolidate" snapshot (fusionner delta avec base)
Libère espace disque supplémentaire

LIMITATIONS :\n - Snapshots = fichiers delta supplémentaires (consomme espace)
- Plusieurs snapshots imbriqués = ralentit performance
- Snapshot != Backup (perte si disque crash)\n - Rollback perd données écrites après snapshot (à prendre en compte productions)

Bonne pratique : Snapshots court-terme seulement, backup pour long-terme
Exercice 5 : Migration VM
VM s'exécute sur serveur physique hôte1. Migrer vers hôte2 sans downtime. Quel mode réseau évite problèmes IP ?
Correction :

Scénario migration :\n hôte1 (vSphere) : VM-Web (IP 192.168.1.100)
hôte2 (vSphere) : (destination vide)

Live Migration (sans downtime) :\n 1. hôte1 → hôte2 : Vérifie ressources disponibles
2. hôte2 : Alloue vRAM, vCPU
3. hôte1 → hôte2 : Copie disque VM (via réseau fast)
4. Pendant migration : Clients accèdent VM sur hôte1 (normal)\n 5. Moment T : hôte1 pause VM, envoie state mémoire à hôte2
6. hôte2 reprend VM avec exact state → Clients reconnectent (< 1s)\n 7. hôte1 : Libère ressources

Mode réseau crucial :\n
BRIDGE ✓✓
- VM garde IP 192.168.1.100 après migration
- Clients qui se connectaient à 192.168.1.100 trouvent toujours
- Pas de changement de route réseau
- Requête ARP : "Qui a 192.168.1.100" → hôte2 répond
- Transparent pour clients

NAT ✗
- VM a IP virtuelle qui dépend de hyperviseur source
- Migration = changement architecture, clients perdus
- Nécessite reconfiguration firewall ports

Host-Only ✗
- VM isolée, pas accès réseau productif

CONCLUSION : Bridge obligatoire pour migration sans reconfiguration client
