1. Principes DICP

DICP = Disponibilité, Intégrité, Confidentialité, Preuve. Les 4 piliers de la sécurité de l'information.

Disponibilité : Les données et services doivent être accessibles aux utilisateurs autorisés quand ils en ont besoin. Protection contre les pannes, attaques DoS (Denial of Service), perte de données.
Intégrité : Les données ne doivent pas être modifiées sans autorisation. Vérification que les données reçues sont exactement celles envoyées. Utilise les fonctions de hachage (hash), signatures numériques.
Confidentialité : Les données sensibles ne doivent être accessibles qu'aux personnes autorisées. Protection par chiffrement, contrôle d'accès, authentification.
Preuve (ou Traçabilité/Authentification) : Vérifier l'identité de l'utilisateur et tracer les actions. Logs, audit trails, non-répudiation (impossible de nier une action).
Exemple application DICP : Banque en ligne : - Disponibilité : serveurs redondants, pas de panne - Intégrité : validation des virements, checksum sur transactions - Confidentialité : chiffrement HTTPS, authentification MFA - Preuve : logs de connexion, historique transactions, certificats numériques

2. Cryptographie Symétrique et Asymétrique

Deux approches pour chiffrer les données et sécuriser les communications.

Cryptographie Symétrique : Une seule clé partagée pour chiffrer et déchiffrer. Clé secrète doit être transmise en sécurité. Exemples : AES (256-bit), DES (obsolète), 3DES. Rapide, utilisé pour chiffrer les données.
Cryptographie Asymétrique (Clé Publique) : Deux clés : publique (partagée) et privée (secrète). Données chiffrées avec clé publique, déchiffrées avec clé privée. Exemple : RSA (2048-bit). Lent, utilisé pour échange de clés et signatures.
Comparaison : Symétrique (AES) : Clé : 256 bits Vitesse : Très rapide ✓ Échange de clé : Problématique (doit être sécurisé) Cas d'usage : Chiffrer données stockées Asymétrique (RSA) : Clés : 2048-4096 bits Vitesse : Lent (100x plus que AES) Échange de clé : ✓ Clé publique partageable Cas d'usage : Signature numérique, établir session sécurisée Combinaison (HTTPS/TLS) : RSA pour échanger clé de session → AES pour chiffrer données Meilleur des deux mondes : sécurité + performance

3. Authentification et MFA

Vérifier l'identité réelle de l'utilisateur avant d'accorder l'accès.

Facteurs d'authentification :
1. Quelque chose qu'on connaît (mot de passe, PIN)
2. Quelque chose qu'on possède (carte, téléphone, clé USB)
3. Quelque chose qu'on est (biométrie : empreinte, iris)
MFA (Multi-Factor Authentication) : Utiliser au minimum 2 facteurs différents. Exemple : mot de passe + code SMS, mot de passe + empreinte, mot de passe + clé de sécurité hardware.
Méthodes courantes : TOTP (Time-based One-Time Password : Google Authenticator), SMS/Email (code temporaire), Push notification (approuver sur téléphone), Biométrie (empreinte digitale, reconnaissance faciale).
Flux authentification MFA : 1. Utilisateur entre login + mot de passe 2. Serveur valide identifiants 3. Demande deuxième facteur : "Entrez code 6 chiffres de l'appli Authenticator" 4. Utilisateur entre code TOTP (valide 30 secondes) 5. Serveur valide → Accès autorisé Avantage : Même si mot de passe compromis, attaquant ne peut pas accéder sans 2e facteur

4. Menaces et Attaques Courantes

Principaux vecteurs d'attaque et menaces en cybersécurité.

Phishing : Email/message trompeur mimant une organisation connue (banque, PayPal) pour voler identifiants. Lien malveillant → page fake → vol de credentials.
Ransomware : Logiciel malveillant chiffrant les données puis demandant rançon pour décrypter. Vecteurs : email, USB, téléchargement. Protection : sauvegardes offline, antivirus, patch système.
Man-in-the-Middle (MITM) : Attaquant intercepte communication entre client et serveur. Lit/modifie données. Protection : HTTPS (chiffrement), VPN, certificats.
Brute Force : Tenter tous les mots de passe possibles jusqu'à trouver le bon. Protection : MFA, limitation tentatives, mot de passe fort, captcha.
DoS/DDoS : Submerger serveur de requêtes pour le rendre indisponible. DoS = une machine, DDoS = plusieurs. Protection : pare-feu, limitation débit, CDN.
Exemple phishing : EMAIL reçu : De : "support@paypal.fr" (adresse usurpée) Objet : "Confirmez votre identité" Corps : "Cliquez ici pour vérifier votre compte" → Lien vers paypa1.com (similaire à paypal.com) Utilisateur clique → Page fake → Entre email + mdp → Mdp volé

Exercices Pratiques

Exercice 1 : Analyse Menace DICP
Une base de données client est compromised. Analysez l'impact sur la Disponibilité, Intégrité, Confidentialité et Preuve. Proposez des correctifs.
Correction :

Scénario : Attaque ransomware sur base de données clients

DISPONIBILITÉ ❌
- Impact : Données inaccessibles, services en panne
- Correctif : Sauvegarde offline régulière, isolation réseau machines critiques, plan de continuité

INTÉGRITÉ ⚠️
- Impact : Données modifiées par attaquant, impossible de savoir lesquelles
- Correctif : Monitoring base de données, checksums, audit trail, signatures numériques

CONFIDENTIALITÉ ❌
- Impact : Données client (email, téléphone) exposées, risque vol identité
- Correctif : Chiffrement base de données, contrôle d'accès strict, RGPD compliance

PREUVE ⚠️
- Impact : Logs supprimés/modifiés par attaquant
- Correctif : Logs centralisés sécurisés, write-once storage, audit immuable
Exercice 2 : Choix Chiffrement
Vous devez chiffrer 1) Les données au repos sur serveur 2) Les identifiants lors de l'authentification. Quel algorithme pour chaque cas et pourquoi ?
Correction :

1) Données au repos sur serveur
→ Utiliser : AES-256 (symétrique)
→ Raison : Chiffrement/déchiffrement rapide (données relues régulièrement)
→ Clé stockée ailleurs (HSM hardware security module) ou dérivée de mot de passe maître
→ Exemple : PostgreSQL avec pgcrypto, MySQL avec TDE

2) Identifiants lors authentification
→ Cas A : Client → Serveur : HTTPS/TLS avec RSA (asymétrique) pour handshake, puis AES pour session
→ Cas B : Stocker mot de passe : HASH (bcrypt, PBKDF2) NON CHIFFREMENT
→ Raison : Plus rapide (handshake TLS 100ms vs RSA plusieurs secondes si toute session)
→ Protection complète HTTPS : authenticité (certificat) + confidententialité (chiffrement) + intégrité (MAC)

Conclusion :
- Au repos : Symétrique (AES) pour vitesse
- En transit : Asymétrique (RSA) + Symétrique (AES) ensemble = TLS/HTTPS
Exercice 3 : Attaque Phishing
Vous recevez email "Urgent : Vérifiez votre compte bancaire" avec lien. Comment identifier le phishing ? Que faire ?
Correction :

Signes d'alerte phishing :

1. Vérifier l'adresse email source
- Légitime : support@banquename.com
- Fake : support@bancname.org, sppourt@bancname.com, support.bancname@fake.com

2. Hoverer sur le lien (NE PAS CLIQUER)
- Affiche URL réelle en bas navigateur
- Fake : https://bancname123.ru (domaine suspect)
- Légitime : https://www.bancname.com

3. Vérifier certificat SSL
- Cliquer sur cadenas → vérifier propriétaire certificat
- Nom domaine doit correspondre

4. Demander identité : Urgence artificielle, syntaxe bizarres ("vérifiez votre account")

QUE FAIRE :
✗ Ne PAS cliquer sur le lien
✗ Ne PAS télécharger pièce jointe
✓ Supprimer l'email
✓ Signaler comme spam/phishing à votre banque directement (pas via email reçu)
✓ Si données entrées : changer mdp immédiatement, surveillance compte
Exercice 4 : Implémentation MFA
Configurez MFA pour une application web avec : mot de passe + TOTP (Google Authenticator). Décrivez le flux et la sécurité.
Correction :

Architecture MFA avec TOTP :

Enregistrement (Setup) :
1. User va dans "Paramètres → Sécurité → Activer 2FA"
2. Application génère secret TOTP (base32 encodé)
3. QR code affiché → User scanne avec Google Authenticator
4. Appli demande d'entrer un code TOTP pour confirmer (preuve que phone a bien le secret)
5. Secret stocké BASE DE DONNÉES (chiffré avec clé maître)

Login avec MFA :
1. User entre email + mdp
2. Serveur valide credentials → OK
3. Serveur affiche prompt "Entrez code 6 chiffres de votre appli Authenticator"
4. User regarde son téléphone → Google Auth affiche code TOTP (renouveau toutes les 30s)
5. User entre code (ex: 234567)
6. Serveur valide :
- Récupère secret du user en BD
- Génère codes TOTP attendus pour ±30 secondes\n - Compare avec code entré\n - Si match → Accès autorisé

Sécurité TOTP :
- Secret jamais transmis une fois enregistré
- Codes temporaires (30s expiration)
- Impossible de rejouer code (expiré)
- Même si serveur hacké, codes passés invalides
- Protection contre : brute force mdp, phishing (mdp seul), replay
Exercice 5 : Détection Attaque MITM
Un utilisateur se connecte via WiFi public. Comment détecter qu'un attaquant intercepte sa connexion ? Quelles protections utiliser ?
Correction :

Attaque MITM possible sur WiFi public :

Détection (difficile sans outils) :
1. Demander certificat HTTPS à destination
- Cliquer cadenas → Vérifier propriétaire certificat\n - Si certificat auto-signé ou nom domaine différent = ALERTE

2. Vitesse internet anormale (attaquant inject malware/ralentit)

3. Outils pour tech :
- tcpdump : Capturer paquets réseau, voir trafic non chiffré
- wireshark : Analyser protocoles, détecter requêtes DNS suspectes
- arp-scan : Détecter ARP spoofing

PROTECTIONS (Préventif) :

1. HTTPS obligatoire ✓
- Chiffre contenu (attaquant ne peut pas lire données)\n - Vérifie authenticité serveur (certificat)\n - Impossible MITM sans certificat valide

2. VPN ✓✓
- Chiffre TOUT le trafic (DNS, HTTP, tout)\n - Attaquant voit seulement "utilisateur 192.168.1.5 → VPN serveur 1.2.3.4"\n - Protection complète

3. MFA ✓
- Si session hijackée, attaquant a besoin 2e facteur

4. Certificat épinglage ✓\n - App mobile force le certificat serveur exact (pas nouveau certificat fake)\n\nBest practice WiFi public : VPN + HTTPS + MFA = Triple protection
